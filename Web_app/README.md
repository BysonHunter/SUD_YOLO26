# SUD YOLO26 · Web

Веб-приложение для загрузки DICOM-архива, подготовки проекций, детекции YOLO26, расчёта параметров камней, интерактивного просмотра и скачивания PDF. Работает рядом с [настольным приложением](../Application/), используя его вычислительные модули и обученную модель. Код настольного приложения не изменён.

## Быстрый запуск через Docker

Нужен **весь репозиторий**, включая [Application/src](../Application/src/) и [веса](../Application/weights/kidney_yolo26.pt). Копирования только этой папки недостаточно. Обучающий датасет и каталоги пациентов серверу не нужны.

Установите Docker Engine с Compose v2 на Linux либо Docker Desktop с Linux-контейнерами на Windows. Для первого запуска потребуется Интернет для загрузки образов и Python-пакетов. Для обработки одного большого исследования предусмотрено до 12 ГиБ RAM на worker; хосту желательно иметь 16–32 ГиБ RAM и запас диска от 30 ГиБ. Каждая дополнительная копия worker увеличивает потребление памяти.

В терминале перейдите в эту папку:

```powershell
cd C:\WorkDOCS\PROJECTS\SUD_YOLO26\Web_app
python configure.py
docker compose up -d --build
docker compose ps
```

В Linux используются те же команды после перехода в `Web_app`. Скрипт [configure.py](./configure.py) создаёт `.env` со случайными паролями; существующий файл не заменяет. Для него нужен Python 3.11 или новее. Если Python на сервере отсутствует, создайте `.env` на другом компьютере и перенесите его отдельно по защищённому каналу.

Откройте **http://localhost:8080**. Логин `admin`, начальный пароль — значение `SUD_BOOTSTRAP_PASSWORD` в локальном `.env`. После смены пароля используйте свой новый пароль: повторная инициализация сервера его не сбрасывает. Не публикуйте этот файл. Начальная конфигурация привязана к `127.0.0.1`, работает по HTTP и предназначена для локальной проверки. Пароли, DICOM, результаты и рабочие окружения исключены из Git и контекста сборки Docker.

Также работает **http://127.0.0.1:8080**: локальные имена `localhost` и `127.0.0.1` допускаются на одном порту и с одним протоколом. Сторонние сайты и другие порты не допускаются. Порт `8086` использовался только при разработке и для обычного запуска не нужен. В поле пароля вводится само значение после `SUD_BOOTSTRAP_PASSWORD=`, а не имя этой переменной.

Проверить конфигурацию без вывода секретов:

```powershell
docker compose config --quiet
docker compose logs --tail=100 worker
```

Не прикладывайте полный вывод `docker compose config` или журналы заданий к публичным обращениям: они могут содержать секреты или идентификаторы пациентов.

### Пользователи и пароли

Войдите под `admin` и откройте **«Пользователи»** в левом меню. В форме создания
укажите логин (3–80 латинских букв, цифр или символов `_.@-`, первый символ — буква
или цифра) и пароль (12–128 символов). Логин сохраняется в нижнем регистре.
Кнопка **«Создать пользователя»** добавляет обычную учётную запись без прав
администратора. Пароль передайте пользователю лично; система не показывает
сохранённые пароли и их хеши.

В таблице показаны роль, статус и число исследований. Кнопка **«Удалить»**
открывает подтверждение с логином выбранного пользователя. После подтверждения
пользователь исчезает из списка, вход запрещается, все сеансы закрываются.
Исследования и их результаты сохраняются на сервере с прежним владельцем;
выполняющиеся задания могут завершиться. Удалённый логин зарезервирован и не
передаёт данные новой учётной записи. Самого `admin` удалить нельзя. Обычные
пользователи не видят этот раздел и не имеют доступа к его API.

Каждый пользователь, включая `admin`, может нажать **«Сменить пароль»** в нижней
части левого меню. Укажите текущий пароль, новый и его повтор. После сохранения
текущий сеанс обновляется, остальные сеансы этой учётной записи закрываются.
Новый пароль хранится в БД как хеш scrypt с индивидуальной солью и сохраняется
после перезапуска контейнеров. Открытые пароли в БД не записываются.

Обновление схемы существующей БД выполняет команда `python -m sudweb.manage init`;
при запуске Compose её автоматически выполняет сервис `initialize`. Данные
пользователей и исследований при обновлении не переносятся и не удаляются.

### NVIDIA GPU

Для Linux нужен драйвер NVIDIA и NVIDIA Container Toolkit. Для Windows используется поддержка GPU Docker Desktop/WSL2. Проверка внутри контейнера обязательна; наличие видеокарты на хосте само по себе не подтверждает её доступность контейнеру. RTX 3090 поддерживает используемую сборку PyTorch с CUDA 12.8 при подходящем драйвере.

```powershell
docker compose -f compose.yaml -f compose.gpu.yaml up -d --build
docker compose -f compose.yaml -f compose.gpu.yaml exec worker python -c "import torch; print(torch.cuda.is_available()); print(torch.cuda.get_device_name(0))"
```

Описание настроек GPU: [документация Docker](https://docs.docker.com/compose/how-tos/gpu-support/). Оставляйте **один worker на одну GPU**, пока не измерены VRAM и время обработки. GPU ускоряет детекцию; чтение DICOM, подготовка проекций, расчёты и построение поверхностей также используют CPU.

### Несколько пользователей и фоновые задания

Создайте отдельные учётные записи:

```powershell
docker compose exec api python -m sudweb.manage user doctor01
docker compose exec api python -m sudweb.manage password doctor01
docker compose exec api python -m sudweb.manage disable doctor01
docker compose exec api python -m sudweb.manage sessions-prune
```

Пароль запрашивается в терминале, в командной строке не передаётся; минимум 12 символов. Публичной регистрации нет. Замена пароля и отключение пользователя отзывают его сессии. Bootstrap-пароль применяется только при создании первого аккаунта; редактирование `.env` не меняет пароль существующего пользователя.

Пользователи могут одновременно загружать архивы и просматривать свои результаты. Один worker последовательно обрабатывает задания; API продолжает отвечать, пока идут тяжёлые расчёты. Для параллельных CPU-расчётов:

```powershell
docker compose up -d --scale worker=2
```

Два worker могут потребовать до 24 ГиБ RAM, помимо API, PostgreSQL и ОС. Не масштабируйте GPU-вариант этой командой на одну карту. Каждый worker берёт следующее задание через блокировку строки PostgreSQL `FOR UPDATE SKIP LOCKED`. Повторная обработка после аварии не запускается автоматически в том же каталоге: просроченное задание помечается ошибкой, пользователь загружает архив повторно.

## Как работать

1. Войдите под своей учётной записью. В разделе **«Исследования»** выберите ZIP-архив с DICOM. Можно перетащить файл на область загрузки. Поддерживается ZIP без пароля; RAR/7z и архивы внутри архивов не распаковываются. Сохраните исходную структуру и `DICOMDIR`, если он имеется.
2. Дождитесь статуса **«Готово»**. В карточке видны стадия и прогресс. Страницу можно закрыть: очередь и результаты хранятся на сервере. Доступна отмена ожидающего или выполняющегося задания.
3. Нажмите **«Открыть»**. При нескольких подходящих сериях выберите нужную в верхней строке. ID пациента, дата исследования и описание серии читаются из DICOM. Автоматический выбор предпочитает серии с признаками native; это совпадает с текущей настольной логикой и не является подтверждением отсутствия контраста.
4. В разделе **«Изображения и детекции»** переключайте аксиальную и корональную проекции. Детекция выполняется на корональных изображениях — именно для них обучена модель. Аксиальные доступны для просмотра. Слои отсортированы численно по номеру, а не как строки. Переключатель «Только с детекциями» оставляет изображения с принятыми моделью объектами.
5. Масштабируйте колесом или кнопками, перемещайте изображение мышью. Координаты отсчитываются от левого нижнего угла изображения в миллиметрах. Сетка при исходном масштабе — 5 мм, при увеличении — 1 мм; шкала адаптирует частоту подписей, чтобы они не перекрывались. Под изображением указаны его полный размер и размер видимой части. Пространственный шаг берётся из геометрических sidecar-файлов экспорта.
6. В разделе **«Параметры и 3D»** выберите почку и камень. Здесь показаны размеры, объём, масса, плотность, HU и номера слоёв, а также рисунки, полученные исходным модулем расчёта. Сетка просмотра КТ на эти рисунки не накладывается.
7. Нажмите **«3D камня»**, **«Срез 15%»** или **«3D почки и HU >160»**. Модель можно вращать, перемещать и увеличивать средствами Plotly. Размеры по всем осям — в миллиметрах, пропорции физические. Для почки используются облегчённая розовая оболочка ROI и отдельная поверхность плотных участков HU >160. Оболочка приблизительная, не анатомическая сегментация. Облегчение поверхностей влияет только на отображение; параметры считаются по исходным вокселям.

Начальный ракурс соответствует корональному снимку: X вправо, Z вверх, Y в глубину.
Преобразование учитывает, что сохранённые массивы анализа идут по строкам снимка
сверху вниз; сами HU-массивы и расчётные параметры не изменяются.

После обновления версии с исправленной ориентацией обновите сохранённые 3D-модели
и их иллюстрации у завершённых заданий (без повторного чтения DICOM и детекции):

```powershell
docker compose exec -e PYTHONPATH=/opt/sud/Application/src:/opt/sud/Web_app/backend worker python -m sudweb.refresh_visuals
```

Команда заменяет только производные JSON-модели и иллюстрации HU/плотности.
Сохранённые PDF сохраняют прежний вид; новые отчёты создаются с исправленной
ориентацией после нового расчёта. Во время обновления оставьте браузерный просмотр
закрытым; после завершения заново откройте результат.
8. В разделе **«Время разрушения»** показана таблица для камня, выбранного в предыдущем разделе. Цвет каждой ячейки, название режима и легенда совпадают с PDF. Наведите мышь, переведите фокус клавиатурой либо нажмите ячейку для подсказки. Используется исходная формула приложения; интерфейс не добавляет неподтверждённые единицы времени или новые критерии режимов.
9. Нажмите **«Скачать PDF»** в верхней строке. Отчёт формируется отдельно для выбранной серии. После завершения работы используйте **«Выйти из системы»**. Удаление карточки удаляет исходный архив и все результаты **только этого задания**.

Если исходный расчёт не может сформировать ROI из детекций почек, результат открывается с явным предупреждением: доступны изображения и детекции, расчёт и PDF недоступны. Это не трактуется как отсутствие камней. Другие ошибки обработки показываются в карточке; подробности доступны администратору в журнале задания. Техническая успешность обработки не подтверждает клиническую точность модели.

## Устройство проекта

```text
SUD_YOLO26/
├── Application/                # общие алгоритмы и обученная модель, без изменений
└── Web_app/
    ├── backend/sudweb/
    │   ├── api.py              # вход, загрузка, авторизация доступа ко всем результатам
    │   ├── db.py               # пользователи, сессии, задания и очередь PostgreSQL
    │   ├── security.py         # scrypt-пароли и хеширование сессионных токенов
    │   ├── archive.py          # ограниченная безопасная распаковка ZIP
    │   ├── worker.py           # очередь, heartbeat, отмена, таймаут, контроль объёма
    │   ├── pipeline.py         # отдельный процесс DICOM → YOLO26 → параметры
    │   ├── artifacts.py        # JSON-манифест, сетки для 3D, общая цветовая таблица
    │   └── manage.py           # администрирование учётных записей
    ├── static/                # интерфейс без Node.js и сторонних CDN
    ├── tests/                 # проверки доступа, очереди, ZIP и согласованности расчётов
    ├── Dockerfile             # лёгкий API и отдельный вычислительный worker
    ├── compose.yaml           # PostgreSQL + инициализация + API + CPU worker
    ├── compose.gpu.yaml       # дополнение для NVIDIA
    ├── configure.py           # создание локальных секретов
    └── var/                   # только локальная разработка; исключён из Git
```

### Изоляция и хранение

Внутри Docker данные находятся в именованном томе `studies`:

```text
/data/users/<UUID пользователя>/jobs/<UUID задания>/
├── input.zip
├── input/                     # распакованные файлы только этого задания
├── export/<PatientID>/<StudyDate>/V001/
│   ├── images/{axial,coronal}/
│   ├── geometry/              # физические координаты и шаги
│   └── volume/                # HU-массивы
├── runtime/                   # собственные настройки YOLO/Matplotlib
├── result.json                # внутренний манифест результатов
├── progress.json
└── worker.log
```

Изолируется **UUID задания**, поэтому одинаковые ID пациентов и имена архивов не пересекаются. Все изображения, сетки, предпросмотры и PDF выдаются через проверку владельца задания; том данных не опубликован статическим веб-каталогом. API не принимает произвольные файловые пути. Сессионные токены хранятся в БД в виде SHA-256, cookie имеет HttpOnly/SameSite, изменения требуют CSRF-токен. Файлы ZIP проверяются на выход из каталога, ссылки, специальные и повторяющиеся пути, число файлов и суммарный размер. Никакие загруженные pickle, Python-код и веса не исполняются; используются только модель и модули из установки сервера.

Каждое задание выполняется новым Python-процессом. Это важно: исходный расчёт использует глобальное состояние и Matplotlib. Кэш, каталоги, параметры YOLO и настройки шрифтов не разделяются между исследованиями. Отмена завершает процесс; состояние очереди переживает перезапуск API. Потеря heartbeat worker обнаруживается по lease (90 секунд).

По умолчанию: ZIP до 2 ГиБ, распаковка до 8 ГиБ и 20 000 записей, до 8 подходящих серий, до 300 млн вокселей на серию; время задания до часа. Compose допускает 3 активных и 30 сохранённых заданий на пользователя. Worker периодически контролирует объём задания (16 ГиБ) и пользовательских данных (40 ГиБ); это контроль с интервалом, не файловая квота ОС. Меняйте пределы через переменные в [compose.yaml](./compose.yaml), учитывая память и диск. Автоматического удаления готовых исследований нет.

Обученные веса подключаются worker только для чтения из [Application/weights](../Application/weights/). При обновлении модели сохраните совместимость шести классов и YOLO26 end-to-end головы. Перезапустите worker; уже полученные результаты остаются прежними.

## Доступ с других компьютеров

Для серверного использования установите HTTPS reverse proxy (например, nginx или Caddy). API по умолчанию слушает только loopback. Настройте в `.env`:

```dotenv
SUD_PUBLIC_ORIGIN=https://sud.example.org
SUD_SECURE_COOKIE=true
SUD_BIND=127.0.0.1
```

Проксируйте на `http://127.0.0.1:8080`, сохраняйте Host и не включайте буферизацию upload на диске без контроля доступа. Если proxy сам работает в Docker, подключите его к сети этого Compose и проксируйте на `api:8080`; прямую публикацию API можно убрать. Лимит тела запроса proxy должен соответствовать 2 ГиБ, таймаут загрузки — размеру архива. Внешний доступ к PostgreSQL и томам не нужен. Порт 8080, привязанный к `127.0.0.1`, не доступен извне непосредственно.

В конфигурации FastAPI не включено доверие произвольным forwarded-заголовкам. При reverse proxy ограничитель входа по IP видит сам proxy; ограничение по аккаунту сохраняется. Внешнее ограничение запросов по реальному клиентскому IP настраивается на доверенном proxy. Не включайте кэширование `/api/` и не публикуйте журналы/каталоги пациентов. Для реального размещения отдельно настройте резервное копирование, сроки хранения, права доступа и правила работы с персональными данными организации.

## Обслуживание

```powershell
docker compose logs --tail=100 api worker
docker compose restart worker
docker compose down
docker compose up -d
```

`down` сохраняет тома. **`down -v` удаляет БД и исследования**, поэтому для обычной остановки его не используйте. Для резервной копии согласованно сохраните PostgreSQL (например, `pg_dump`) и том `studies`; на время копирования остановите загрузки и worker. `.env` храните отдельно. При восстановлении необходимы оба тома/дамп и данные: файлов без записей БД или одной БД без файлов недостаточно. Отключение пользователя блокирует HTTP-доступ, но уже запущенное задание само по себе не отменяет — его может завершить worker.

## Локальная разработка и тесты

Python 3.11. Создайте отдельное окружение, установите [requirements-dev.txt](./requirements-dev.txt). Для worker дополнительно нужны PyTorch и зависимости [настольного приложения](../Application/requirements.txt), установленные с его [constraints.txt](../Application/constraints.txt). Окружение настольного приложения изменять не требуется.

Пример PowerShell из этой папки после установки зависимостей:

```powershell
$env:PYTHONPATH = "$PWD/backend"
$env:PYTHONDONTWRITEBYTECODE = '1'
$env:SUD_SECURE_COOKIE = 'false'
python -m sudweb.manage init
python -m sudweb.manage user developer
python -m uvicorn sudweb.api:create_app --factory --host 127.0.0.1 --port 8080 --no-access-log
```

Во втором терминале с теми же переменными и окружением:

```powershell
python -m sudweb.worker
```

Без `DATABASE_URL` используется SQLite в локальной `var` — только для разработки на одном хосте. Для развёртывания и нескольких worker используйте PostgreSQL из Compose. Проверки:

```powershell
$env:PYTHONPATH = "$PWD/backend"
python -m unittest discover -s tests -v
```

Для полного теста нужны общие вычислительные зависимости. Проверка загрузки DICOM на CPU/GPU и контейнерной установки отличается от unit-тестов; фактически выполненные проверки записаны в конце этого документа.

После сборки worker те же тесты можно выполнить в контейнере:

```powershell
docker compose run --rm --no-deps --volume "${PWD}/tests:/opt/sud/Web_app/tests:ro" worker python -m unittest discover -s /opt/sud/Web_app/tests -v
```
